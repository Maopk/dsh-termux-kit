# Languages: English source, switchable at runtime

**Source text is English** — that is the face of a public repo. Chinese is not *translated away*; it comes back
through a small lookup layer, and the user picks the language with one switch.

## Single source of truth

```
~/.dsh-lang        one line:  zh | en | auto        (missing file behaves as auto)
```

The Console app's switch, the DSH page panel and every shell script read **this same file**, so the app cannot say
“Authorized” while a script answers in Chinese.

`auto` resolves to the system language via `getprop persist.sys.locale`, falling back to `ro.product.locale`.

> Do **not** use `$LANG` for this: inside Termux it is `en_US.UTF-8` by default and has nothing to do with the
> user's preference. Measured on the reference device: `$LANG=en_US.UTF-8` while `ro.product.locale=zh-CN`.

## Shell side — `widgets/i18n.sh`

```bash
. i18n.sh
dsh_lang                 # → zh | en
dsh_lang_set zh|en|auto  # writes ~/.dsh-lang (the app's switch does the same thing)
dsh_msg "Some English"   # → Chinese if the current language is zh and the table has it, else unchanged
```

The output helpers in `common.sh` (`step`, `ok`, `warn`, `bad`, `die`, `say`, `log`) route their message through
`dsh_msg`, so the 12 widgets follow the switch **without touching a single call site**.

**Deliberate degradation:** a key that is missing from the table is printed **as English**. A gap therefore shows
one English line — it never prints an empty string, a key name, or an error.

## How the table is built

Chinese originals live in git history, and `git diff` is *aligned by construction*: inside one hunk, a removed
Chinese line and the added English line next to it are a pair. `tools/i18n-build-table` remains available for
mining that history, but it is no longer how the shipped table is maintained — see the next section.

## One source table, two generators

Hand-maintaining one table per runtime is what produced every translation bug this project has had: a string added
to one table and forgotten in another, and — worse — the **opposite escaping rules** of the two runtimes silently
killing whole blocks. There is now exactly one source:

```
i18n/zh.json                  { "English source": "中文" }   ← the only file a human edits
  ├── widgets/i18n.sh            generated block (bash: `declare -A DSH_ZH`)
  ├── apps/bridge/…/Lang.java    generated block (Java HashMap)
  └── apps/console/…/Lang.java   generated block (Java HashMap)
```

The generated blocks sit between `>>> generated by tools/i18n-table` / `<<<` markers and **must not be edited by
hand** — the next `gen` overwrites them.

```bash
tools/i18n-table gen              # rewrite all three generated blocks from i18n/zh.json
tools/i18n-table check            # fail if a generated block drifted from the source (use in CI)
tools/i18n-table add patch.json   # merge {en: zh} pairs into the source, then regenerate
tools/i18n-table missing          # source keys deliberately left untranslated
tools/i18n-table audit <dir>      # user-visible Java literals that have no entry at all
```

### The two runtimes need *opposite* escaping

This is the most expensive bug in the project's history — it made whole blocks ignore the language switch while
looking perfectly fine in the source — so it is stated explicitly:

| Runtime | Lookup | A line break must be stored as | Why |
|---|---|---|---|
| bash | `dsh_msg "…"` | the **two characters** `\` `n` | the value reaches the screen through `printf "$(…)"`, which expands it, and `declare -A` must stay one entry per line |
| Java | `Lang.t("…")` | the **one-character escape** `\n` in the source (a real newline at runtime) | `Lang.t()` compares runtime strings, and the value goes straight to `setText()` |

Writing the bash convention into a `Lang.java` gives a key that never matches its call site: the line silently
stays English, and a translated value would print a literal `\n`. `tools/i18n-table` applies the right rule to each
target, and `tools/i18n-java-fix --check` detects the damage in a hand-edited Java table.

### Which entries go into which app

The bash table carries every entry; each `Lang.java` carries only the entries whose English literal **appears in
that app's own sources** (excluding `Lang.java` itself, or the filter would be self-fulfilling). That test is exact
because a Java lookup is always `Lang.t(<something>)`, where `<something>` is either a literal in the app or a value
assembled from literals in the app (`Tasks.ALL`, panic reasons, `stopListening` reasons…). It is also
self-maintaining: add a `Lang.t("…")` and the next `gen` picks the translation up. Emitting the whole shared table
instead was measured at **+23 KB on a 33 KB APK**.

## App side

Both apps are built with plain `javac` + `android.jar` — there is **no AndroidX**, so
`AppCompatDelegate.setApplicationLocales()` is unavailable. Instead each app keeps a generated in-code table
(`Lang.java`), a `SharedPreferences` choice, and a row “Language: auto / 中文 / English”.
The apps cannot read `~/.dsh-lang` (it lives in Termux's private directory), so the Console writes the file and
**reconciles** with it through a `RUN_COMMAND` query on create/resume — the Termux side stays authoritative.

Two traps, both hit for real:

1. **Translate at render time.** A `static final` array of already-translated labels freezes the language that was
   active when the class was first loaded (`Tasks.ALL` is therefore kept as English source and wrapped in `Lang.t()`
   at the point of display).
2. **Wrap every literal.** A string that never reaches `Lang.t()` can never be translated, however complete the
   table is. `tools/i18n-table audit <app-src-dir>` exists to catch exactly this.

### Deliberately left English

Not everything should be translated. These are **protocol and diagnostics**, read by the agent rather than by the
user, and a translated error is harder to search for:

- the bridge's socket replies (`throw new Exception("Wrong token")`, `"App not found: "`, screenshot errors)
- `Log.*` lines in `WakeReceiver` / `BridgeService`
- task ids (`0_emergency-stop`) and every command path

## Language-neutral data tokens

Some strings are **data**, not display text — do not translate them:

| Token stream | Producer | Consumers |
|---|---|---|
| `【name】完成` / `【name】失败` (legacy) and `[name] done` / `[name] failed` (current) | `widgets/common.sh` (`done_`, `die`) → the widget logs | `tools/dsh-status-pub`, `tools/dsh-tasksd` (parse), `plugins/dsh-mobile-local/client.js` (shows the ✔ badge) |

Those parsers accept **both** spellings and normalize to `done` / `failed`, so logs written before the switch keep
working. If you ever change the marker format, change all four places in the same commit.

## Adding a language

1. Add a second JSON map (`i18n/<lang>.json`) and let `tools/i18n-table` emit one table per language — the block
   markers already isolate the generated region.
2. Extend `dsh_lang`'s system detection and `dsh_msg`'s lookup branch.
3. Add the option to the apps' switch row.

Every call site stays untouched: they all go through `dsh_msg()` / `Lang.t()`.
