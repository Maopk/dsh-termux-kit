# Languages: English source, switchable at runtime

**Source text is English** — that is the face of a public repo. Chinese is not *translated away*; it comes back
through a small lookup layer, and the user picks the language with one switch.

## Single source of truth

```
~/.dsh-lang        one line:  zh | en | auto        (missing file behaves as auto)
```

The Console app's switch, the DSH page panel and every shell script read **this same file**, so the app cannot say
“Authorized” while a script answers in Chinese.

`auto` resolves to the system language via `getprop persist.sys.locale`, falling back to `ro.product.locale`.

> ⚠ Do **not** use `$LANG` for this: inside Termux it is `en_US.UTF-8` by default and has nothing to do with the
> user's preference. Measured on the reference device: `$LANG=en_US.UTF-8` while `ro.product.locale=zh-CN`.

## Shell side — `widgets/i18n.sh`

```bash
. i18n.sh
dsh_lang                 # → zh | en
dsh_lang_set zh|en|auto  # writes ~/.dsh-lang (the app's switch does the same thing)
dsh_msg "Some English"   # → Chinese if the current language is zh and the table has it, else unchanged
```

The output helpers in `common.sh` (`step`, `ok`, `warn`, `bad`, `die`, `say`, `log`) route their message through
`dsh_msg`, so the 10 widgets follow the switch **without touching a single call site**.

**Deliberate degradation:** a key that is missing from the table is printed **as English**. A gap therefore shows
one English line — it never prints an empty string, a key name, or an error.

## How the table is built

Chinese originals live in git history, and `git diff` is *aligned by construction*: inside one hunk, a removed
Chinese line and the added English line next to it are a pair.

```bash
tools/i18n-build-table --report     # coverage per file
tools/i18n-build-table --json       # machine-readable, also used to generate the app's Java table
tools/i18n-build-table --write      # rewrite the array inside widgets/i18n.sh
```

> Pairing the two versions **by order of appearance** was tried first and does not work: translations merge two
> lines into one or split one into two, so the whole file drifts out of alignment. The diff-based pairing is the
> reliable one.

## App side

Both apps are built with plain `javac` + `android.jar` — there is **no AndroidX**, so
`AppCompatDelegate.setApplicationLocales()` is unavailable. Instead each app keeps a small in-code table
(`L.java`) with the same English→Chinese pairs, a preference, and a settings row
“Language: System / 中文 / English” that calls `recreate()` so the screen is redrawn immediately.

## Language-neutral data tokens

Some strings are **data**, not display text — do not translate them:

| Token stream | Producer | Consumers |
|---|---|---|
| `【name】完成` / `【name】失败` (legacy) and `[name] done` / `[name] failed` (current) | `widgets/common.sh` (`done_`, `die`) → the widget logs | `tools/dsh-status-pub`, `tools/dsh-tasksd` (parse), `plugins/dsh-mobile-local/client.js` (shows the ✔ badge) |

Those parsers accept **both** spellings and normalize to `done` / `failed`, so logs written before the switch keep
working. If you ever change the marker format, change all four places in the same commit.

## Adding a language

1. Add a table next to `DSH_ZH` in `widgets/i18n.sh` and one branch in `dsh_msg`.
2. Extend `dsh_lang`'s system detection.
3. Add the same pairs to the apps' `L.java`.
4. Add the option to the app's switch row.

Nothing else in the codebase needs to know about it.
